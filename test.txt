Yes — this is a very common and sensible practice, especially once a project has multiple frontend/backend teams.

The important distinction is that the YAML is usually an API contract, rather than a generic config file.

A typical setup looks like:

project/
├── api/
│   └── openapi.yaml              # source of truth
│
├── backend/
│   ├── generated/
│   │   └── schemas.py            # generated Pydantic models
│   ├── models/
│   ├── services/
│   └── routes/
│
├── frontend/
│   ├── generated/
│   │   ├── models.ts             # generated TS types
│   │   └── api.ts                # generated API client
│   ├── components/
│   └── pages/
│
└── scripts/
    └── generate_api.py

The workflow becomes:

                 openapi.yaml
                      │
              ┌───────┴────────┐
              │                │
              ▼                ▼
       Python generator   TypeScript generator
              │                │
              ▼                ▼
     backend/generated/   frontend/generated/
              │                │
              ▼                ▼
        Backend code       Frontend code

For example
Your OpenAPI definition says:

components:
  schemas:
    User:
      type: object
      required:
        - id
        - name
      properties:
        id:
          type: integer
        name:
          type: string
        email:
          type: string

You might generate:

# backend/generated/schemas.py

class User(BaseModel):
    id: int
    name: str
    email: str

And simultaneously:

// frontend/generated/models.ts

export interface User {
    id: number;
    name: string;
    email: string;
}

You could even generate an API client:

// frontend/generated/api.ts

export async function getUser(id: number): Promise<User> {
    ...
}

Then developers don't manually maintain those types.

They write application code against them:

# backend/services/user_service.py

def get_user(...) -> User:
    ...

and:

// frontend/components/UserProfile.tsx

function UserProfile({ user }: { user: User }) {
    return <div>{user.name}</div>;
}

There's an even more interesting variation
You don't necessarily have to make the YAML the source of truth.

There are roughly three common approaches.

1. OpenAPI-first
openapi.yaml
     │
     ├──→ Pydantic
     │
     ├──→ TypeScript
     │
     └──→ API client

This is what you're describing.

The API specification is written first, and code is generated from it.

This works particularly well when you have separate frontend/backend teams because the API contract exists independently of either implementation.

2. Backend-first
The backend code defines the schema:

class User(BaseModel):
    id: int
    name: str
    email: str

FastAPI, for example, can generate OpenAPI from the Python definitions.

Then:

Pydantic
    │
    ▼
OpenAPI
    │
    ├──→ TypeScript types
    └──→ TypeScript API client

This is also extremely common.

The backend developers don't manually maintain openapi.yaml; the framework generates it.

3. Schema-first with a separate IDL
Some organizations use something like:

Protocol Buffers
GraphQL schema
JSON Schema
OpenAPI

as the contract:

schema
  │
  ├──→ Backend generated code
  ├──→ Frontend generated code
  ├──→ Documentation
  └──→ API clients

This becomes especially useful when there are many consumers.

The really important part: generated code shouldn't be edited
A good convention is:

generated/
    ⚠️ DO NOT EDIT

For example:

backend/
├── generated/        ← machine-owned
│   └── schemas.py
│
├── routes/           ← developer-owned
├── services/         ← developer-owned
└── repositories/     ← developer-owned

And:

frontend/
├── generated/        ← machine-owned
│   ├── models.ts
│   └── api.ts
│
├── components/       ← developer-owned
├── pages/            ← developer-owned
└── hooks/             ← developer-owned

Then your CI can run:

generate
git diff --exit-code generated/

If someone changes the schema but forgets to regenerate the code, CI fails.

And this solves exactly the communication problem you asked about
Suppose the backend team changes:

User:
  properties:
    name:
      type: string

to:

User:
  properties:
    full_name:
      type: string

They run generation:

openapi.yaml
     │
     ├──→ Pydantic User
     │
     └──→ TypeScript User

The frontend's generated type changes:

interface User {
-    name: string;
+    full_name: string;
}

Then existing frontend code:

user.name

produces a TypeScript compilation error.

So instead of someone having to remember:

"Oh, I need to tell Alice on the frontend team that I changed name."

the contract + CI system tells everyone.

That's one of the major benefits of contract-driven development.

One subtle point about your database question
I'd keep database schemas and API schemas separate.

For example:

                 PostgreSQL
                     │
               Alembic migrations
                     │
                     ▼
               SQLAlchemy models
                     │
                     ▼
              Backend domain logic
                     │
                     ▼
                Pydantic API
                     │
                     ▼
                 OpenAPI
                     │
             ┌───────┴────────┐
             ▼                ▼
       TypeScript types    API client
             │                │
             └───────┬────────┘
                     ▼
                  Frontend

Don't generally try to generate your entire API contract directly from the database schema.

For example, your DB might have:

users
├── password_hash
├── internal_notes
├── deleted_at
├── created_at
└── ...

but your API might expose:

{
    "id": 123,
    "name": "John"
}

The database model and API model have different responsibilities.

So yes, the architecture you're imagining is absolutely a real pattern:

                  CONTRACT
                     │
              openapi.yaml
                     │
          ┌──────────┴──────────┐
          ▼                     ▼
   GENERATED CODE         GENERATED CODE
      Python                  TypeScript
          │                     │
          ▼                     ▼
       Backend              Frontend
       developers            developers

And in a well-designed system, developers treat the generated directory as read-only and treat the contract as the thing they change when the interface needs to change.
